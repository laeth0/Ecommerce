# System Design Prerequisites & Concepts to Learn

**Objective:** explain each mechanism and its safety boundary before implementation. Read [Checkout's prerequisites](../06-checkout/system-design-prerequisites.md) first; finance adds an external authority and finite deduplication retention.

| Concept | Mental model and concrete problem | Cost/failure to understand | Study and practical experiment |
| --- | --- | --- | --- |
| Idempotency at three boundaries | Client key deduplicates local acceptance; immutable operation UUID names the financial intent; external key deduplicates provider mutation | The external window expires; a unique local row alone cannot undo a duplicate charge | [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests); lose a response and retry before/after the safety cutoff |
| Unknown versus definitive failure | A timeout describes observation, not money; cancel an existing provider intent and verify zero capture before releasing the uncertainty | Missing ID, 404 or stale search cannot prove no effect; retrying with a new key can charge twice | [Stripe low-level errors](https://docs.stripe.com/error-low-level); cut the response after provider success |
| Durable intent before I/O | Commit Pending and frozen key before dispatch; call without a connection; record response/facts in another short transaction | Crash between commit and send is indistinguishable from a send with lost response | Follow the [system design](system-design.md); stop the process at each boundary |
| Saga orchestration and compensation | Checkout coordinates stock and Order; Payments returns financial proof and reserves full remaining refund coverage | Refund is a new fallible operation; cancellation can be complete while refund remains unresolved | [Existing coordinator](../06-checkout/functional-requirements/checkout-workflows.md); capture after stock expiry and inspect compensation |
| Row locking and write skew | Lock one payment before checking net refund plus all reservations; every contender uses the same order | Lock waits/deadlocks and a hot payment; unlocked SUM plus INSERT can over-reserve | [PostgreSQL explicit locks](https://www.postgresql.org/docs/18/explicit-locking.html); race Admin refunds with automatic compensation |
| Optimistic versioning plus replay | New human mutation requires current financial version; exact accepted replay is checked before new-version/amount guards | Response loss must not create a false stale-version failure; old key with changed body conflicts | [API contract](functional-requirements/api-contracts.md); replay after a provider fact changes version |
| Inbox and at-least-once observation | Verify signature, commit event identity/hint, acknowledge; process later; fact identity deduplicates distinct events | Inbox dedup alone cannot deduplicate API response and a different callback | [Stripe webhooks](https://docs.stripe.com/webhooks); submit duplicate and separately generated events for one object |
| Authenticity versus business authority | Valid signature authenticates sender; account, mode, immutable local mapping, amount and owner proof establish admissible evidence | Signed event metadata can still be mismatched; client success cannot authorize fulfillment | [OWASP REST guidance](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html); use a valid unrelated sandbox object's event |
| Append-only facts and correction | Keep success evidence; append one verified reversal; derive current net balance; never erase history | Current settlement can differ from an earlier public observation | [Stripe asynchronous refunds](https://docs.stripe.com/testing#refunds); observe success then failure and resend old success |
| Leases and fencing | Claim/commit a token; do I/O; revalidate token/time after lock waits; retain independently verified financial evidence | Expired lease does not stop the external system; old responses need safe classification | Kill/restart two workers; delay the first response beyond lease takeover |
| Backpressure and queue stability | Financial service rate must exceed sustained arrival rate; bound provider calls, retries and active work | More application replicas can overload one shared provider account | [Stripe limits](https://docs.stripe.com/rate-limits); measure local workload separately from low-rate provider probes |
| Recovery across an external ledger | Restore local records, then reconcile provider evidence over the lost interval before purchase/fulfillment admission | Finite RPO can lose keys and mappings for money already captured | Follow [restore procedure](deployment-and-devops/configuration-and-operations.md#backups-and-integrated-restore); capture between backup and crash |

## Prerequisite exit criteria

Before PAY-E1 implementation, explain the payment/refund equations, the lock graph and why no connection crosses a provider wait. Before PAY-E2, demonstrate where each key originates, which exact parameters are frozen, and what happens after retention expiry. Before PAY-E3, distinguish signed ingress from verified capture and show how lost wake notifications are recovered. Before PAY-E4, explain partial refunds, Unknown reservations and reversals. Before PAY-E5, present a restore reconciliation plan that finds orphan provider objects.

For every experiment, record initial intent/order/reservation identities, each transaction/response boundary, persisted facts, final balances, business outcome and unresolved work. A synthetic response, unit-only model or documented diagram cannot establish PostgreSQL lock safety, provider semantics, ingress compatibility or integrated recovery.
