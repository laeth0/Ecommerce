# Incident Response and Original-Work Recovery

**Status:** operating procedures for implemented services. No operation is executed by this documentation task.

## Common containment and evidence

Authenticate current protected operator capability, identify exact environment/account/owner and record incident/request ID. Capture release/schema/profile/epoch fingerprints, original target IDs and current gates without secrets. Use protected owner inspection; telemetry locates records but cannot authorize repair.

When integrity, authority, stale process, unknown provider orphan or possible second executor is involved, close affected new admission/dispatch/fulfillment through existing attributed gates and fence unsafe processes/egress. Preserve signed callback ingress/retained observation capacity where safe. Do not stop all local browsing because a private financial class is down.

Never: generate another financial key/window for Unknown, delete coverage, change a terminal decision, clear a hold by elapsed time, invent stock Consume, fabricate a missing accepted Order or delete event/dedup evidence. Every reopening has a recorded evidence owner and outstanding blockers.

## REL-RB-01 — Private peer unavailable or circuit open

1. Determine failed direction/class and whether caller local primary/config/identity is healthy.
2. Inspect actual2s timeouts, circuit transition, offered/dispatched/local rejected counts, slots and pending/deadline age. Verify no HTTP automatic retries/hedging.
3. Check private network, peer readiness, compatible schema/epoch, fixed URL/certificate/trust and pool pressure. Security failure follows RB06 rather than repeated half-open calls.
4. Preserve original scheduled work. Overdue cycles enter review; no borrowed read/command slots or unbounded wait queue.
5. Restore peer path; let one eligible original half-open operation run under normal budget. Inspect actual original receipts/evidence, not only a health200.
6. Resume eligible reviewed originals by attributed operation if the cause changed. Track legitimate progress and review separately.

**Reopen:** compatible current peer/identity, original work accounted for, resource pressure controlled and required financial/restore gates clear. A Closed circuit alone is insufficient.

## REL-RB-02 — Command or Admin refund response unknown

1. Read original Commerce accepted request/authority/key/command bytes and parent work/version. A fresh public replay still requires current human role/network/account.
2. Query Payments original command receipt through existing scope. Compare exact mapping/canonical request and any original public refund receipt.
3. Known Applied/Rejected: apply original immutable result locally under current token/version. Admission202 does not mean refund succeeded.
4. Unknown/missing response: schedule original identity with bounded policy. After restore, a missing record invokes RB07 and cannot prove no effect.
5. If refund admitted, inspect R, original mutation/key/first-send and provider evidence under account quota. No alternate key or replacement Unknown refund.
6. If review, correct root cause and use OriginalOutcomeLookup/CauseCorrected under the [resume guards](../functional-requirements/recovery-and-operating-contracts.md).

**Reopen:** original admission/result knowledge and financial equation/gates sound. Later account revocation does not invalidate already approved immutable intent; it blocks fresh public authority.

## REL-RB-03 — Held, Finalizing or awaiting release

1. Inspect original Commerce confirmation ID/token/capture mapping, Pending/Committed/Aborted decision and actual stock history.
2. Inspect Payments original hold, current terminal-decision knowledge, deferred fixed watermark/unapplied items, integrity flags and work deadline.
3. Pending decision: let original coordinator recheck cancellation/state/primary-clock stock deadline. Never tell Payments to infer a terminal decision.
4. Committed/Aborted: communicate/query that exact decision under existing mTLS schema. An immutable resolution acknowledgement may still mean Finalizing.
5. Resume original finite barrier under owner locks; observe effects through the fixed watermark and actual fact application times.
6. ResolvedCommitted with intact integrity: retrieve exact usable release and record it at Commerce. ResolvedAborted has no fulfillment release.
7. Integrity conflict/missing history: maintain containment and proof-based owner repair. No operator action simply deletes token or sets release=true.

**Reopen fulfillment:** historical confirmation, cancellation guard and matching locally recorded usable release. Consumed stock remains historical; ordinary later refunds do not rewind Order/stock.

## REL-RB-04 — Late capture, Unknown refund or failed compensation

1. Verify original capture/account/object/amount/mapping and actual reservation disposition. Late capture cannot confirm expired/released stock.
2. Read original case C/S/R and refund chains; distinguish covered money from settled money.
3. Retrieve original uncertain provider objects under5/sec/burst2/concurrency2 and original safe-window policy; retain R for Unknown.
4. Definitive Admin failure releases its allocation according to owner rules; original case allocates uncovered gap. Definitive compensation failure retains FailedHold.
5. Protected replacement only after original authoritative terminal failure, exact case/amount and unique repair/replacement chain. A different error message or timeout is not proof.
6. Reversal/changed evidence applies linked correction under normal root/hold/integrity rules and may reopen coverage in the original case.
7. Track current Order safe disposition and actual financial settlement/review separately.

**Reopen:** reconciled original owner equation/coverage and all affected source/integrity gates. Unknown original mutations remain retained review; do not use new purchases to test the account.

## REL-RB-05 — Broker, parking or missing notification

1. Inspect original owner outbox bytes/digest/source/ID/audit or fact, relay claim/count and actual confirm/return result.
2. Inspect queue policy, channel/grant/route, inbox/quarantine and original local sink receipt.
3. Broker unavailable/confirm lost: retain original row and same-ID publication; do not reset transport/financial cycles.
4. Parking/poison: protected individual intake compares trusted canonical owner bytes; commit intake/quarantine before ack. Resolve with original attributed operation and compatible consumer.
5. Financial hint ahead of owner/source missing: quarantine/integrity review; owner query remains authority. Ordinary missing hint uses polling/scan.
6. If storage pressure, follow existing admission gates and recovery reserve; never clear queues/history merely to lower a gauge.

**Reopen:** source identity, effective reliable DLX/bounds, compatible consumer and durable sink evidence are sound. A publish confirm or empty queue does not prove delivery.

## REL-RB-06 — Stale epoch, certificate, role or executor

1. Contain denied capability and preserve evidence. Identify whether the process-frozen epoch, peer certificate/trust, role map or provider executor is wrong.
2. Fence stale provider process/egress and revoke obsolete credentials/session access. Expired lease alone is insufficient.
3. Restore reviewed identity/epoch/configuration through existing protected procedure; do not update a running stale process from current DB epoch as its own identity.
4. Recycle HTTP connections during certificate trust rotation; verify valid and denied identities using actual private routes.
5. Prove exactly one account executor and original mutation keys/windows before dispatch reopens.

**Reopen:** negative identity tests, owner epoch/schema compatibility and old-process/egress fencing established. Timer/circuit closure never repairs authorization.

## REL-RB-07 — Shared primary/storage failure or restore

Follow [paired restore](backup-and-restore.md) for archive/history loss. A simple recovered database connection still needs original overdue-work/claim/result reconciliation.

For disk pressure, inspect owner/WAL/broker/diagnostic volume separately. At70% or<24h horizon warn; at85% or<6h horizon contain new affected admission. Preserve resolution/evidence reserve and separately bounded diagnostic retention. Never truncate authoritative files or delete receipts.

**Reopen:** owner integrity/history/provider gap and safe capacity proven; RTO measured through this point. Missing history remains an explicit blocker.

## REL-RB-08 — ManualReview resume

1. Establish current owner-specific Inspect/Resume capability and exact typed target; fetch current state/version/cause/lease and original evidence.
2. Correct dependency/resource/identity blocker or plan original-outcome retrieval. Review whether the next action is safe and still within original source/window rules.
3. Supply one operation UUID, exact expectedVersion, bounded reason and retained evidence locators. No operatorId in JSON.
4. Owner validates, rejects active lease/stale version, and commits scheduling/receipt/audit atomically. Same operation replays; AlreadyScheduled/Terminal does not reset a budget.
5. Observe actual progress under the new finite cycle; stop further blind resumes if the cause remains unchanged. Record fresh failure/review with original identity intact.

**Close incident:** all original affected records accounted for, unresolved blockers assigned/contained, safe capabilities reopened, failed/Not run evidence retained and an explanation of root cause and recurrence prevention recorded in the protected incident system.
